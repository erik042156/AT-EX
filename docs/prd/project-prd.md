## 1. 프로젝트 개요

- **프로젝트명**: AT-EX (Automation Testing - Automation Exercise)
- **목표**: Automation Exercise 웹 사이트를 대상으로 한 UI 회귀 테스트 자동화 프레임워크 구축

- POM 설계 원칙에 따른 Page Layer/Test Layer 명확한 책임 분리

### 2.2 프로젝트 목표
1. **프레임워크 구축**: Python + Selenium + pytest + POM 기반의 견고한 자동화 프레임워크 개발
2. **테스트 케이스 작성**: 주요 사용자 시나리오에 대한 자동화 테스트 케이스 작성

5. **지속적 개선**: MVP 이후 기능 확장 및 추가 시나리오 포함

### 2.3 기대 효과

## 5. 자동화 대상 범위

### 5.1 주요 기능 (전체 대상 사이트)
Automation Exercise 사이트의 주요 기능:

1. **회원 관리**
   - 회원가입 (Sign up)
   - 로그인 (Login)
   - 로그아웃 (Logout)
   - 계정 정보 수정

2. **제품 관리**
   - 제품 목록 조회
   - 제품 상세 정보 확인
   - 제품 검색 (키워드 기반)
   - 제품 필터링 (카테고리, 가격 등)

3. **장바구니**
   - 장바구니에 제품 추가
   - 장바구니 조회
   - 장바구니 수량 변경
   - 장바구니에서 제품 삭제

4. **주문 및 결제**
   - 결제 페이지로 진행
   - 배송지 정보 입력
   - 결제 정보 입력
   - 주문 완료

5. **기타 페이지**
   - 연락처 (Contact Us)
   - 블로그 (Blog)
   - 회사 정보 (About Us)

### 5.2 MVP 대상 기능 (초기 범위)
MVP(Minimum Viable Product) 단계에서는 **사용자의 핵심 흐름**에 집중합니다:

**우선순위 1 (필수)**:
- 회원가입 (유효한 이메일, 비밀번호 입력)
- 로그인 (회원가입한 계정으로 로그인)
- 로그아웃 (세션 종료)

**우선순위 2 (높음)**:
- 제품 검색 (키워드 기반 검색)
- 제품 목록 조회
- 장바구니에 제품 추가
- 장바구니 조회

**우선순위 3 (중간) - MVP 범위에 포함 시 검토**:
- 결제 프로세스 (배송지 입력, 결제 정보 입력)
- 주문 완료

### 5.3 자동화 세부 범위
- **정상 시나리오**: 사용자가 기능을 의도대로 사용하는 경우 중심
- **비정상 시나리오**: 유효성 검사 오류, 잘못된 입력 처리
- **경계값 테스트**: 입력 값의 극단적 경계 조건
- **페이지 탐색**: 페이지 간 이동, URL 변경, 페이지 로드

## 6. 자동화 제외 범위

### 6.1 MVP에서 제외되는 기능
다음 기능들은 **MVP 단계에서 우선 제외**하며, 추후 확장 범위에 포함:

| 기능 | 이유 |
|------|------|

### 6.2 제외 사유
- 테스트 인프라 구성 복잡도 최소화
- MVP 일정 내 완료 가능한 범위 결정
- 초기 단계에서는 **기본 기능의 견고한 자동화**에 집중

## 7. MVP 대상 기능 (확정)

### 7.1 MVP 스코프
MVP는 **사용자 가입부터 상품 검색 및 장바구니까지의 기본 흐름**을 포함합니다:

**MVP에 포함되는 기능**:
1. **회원가입 (Signup)**
   - 유효한 이메일 및 비밀번호로 계정 생성

2. **로그인 (Login)**

3. **로그아웃 (Logout)**

4. **상품 검색 (Product Search)**
   - 키워드 기반 상품 검색
   - 검색 결과 조회

5. **장바구니 (Shopping Cart)**
   - 상품을 장바구니에 추가
   - 장바구니 내용 확인

### 7.2 MVP 범위에서 제외된 기능 (추후)
- 결제 프로세스
- 주문 이력 조회
- 고급 필터링
- Contact Us 폼 작성

## 9. 주요 사용자 흐름 (Happy Path)

### 9.1 기본 사용자 여정
사용자가 사이트를 방문하여 상품을 검색하고 장바구니에 추가하는 일반적인 흐름:

**단계 1: 사이트 접속 및 회원가입**
1. 사용자가 Automation Exercise 홈 페이지에 접속
2. "Sign up" 버튼/링크를 클릭하여 회원가입 페이지 이동
3. 필수 정보 입력:
   - 이름
   - 이메일 주소
   - 비밀번호
   - 비밀번호 확인
4. "Sign up" 버튼 클릭
5. 회원가입 성공 메시지 또는 확인 페이지 표시
6. 로그인 페이지로 자동 리다이렉트 (또는 자동 로그인)

**기대 결과**: 새로운 계정이 생성되고 로그인 상태로 전환

---

**단계 2: 로그인**
1. 로그인 페이지에 이메일과 비밀번호 입력
2. "Login" 버튼 클릭
3. 로그인 성공 메시지 표시 또는 대시보드 페이지로 이동
4. 상단 네비게이션에 사용자 이름 또는 "Logged in" 상태 표시

**기대 결과**: 사용자가 로그인 상태가 되고 개인화된 콘텐츠에 접근 가능

---

**단계 3: 상품 검색**
1. 홈 페이지 또는 "Products" 페이지로 이동
2. 검색창에 상품 키워드 입력 (예: "dress", "shirt" 등)
3. "Search" 버튼 클릭 또는 엔터 키 입력
4. 검색 결과 페이지 표시
5. 검색 결과에 해당 상품들이 나열됨

**기대 결과**: 입력한 키워드와 관련된 상품들이 검색 결과에 표시됨

---

**단계 4: 장바구니에 상품 추가**
1. 검색 결과 또는 제품 목록에서 원하는 상품 선택
2. 상품 상세 페이지에서 "Add to cart" 버튼 클릭
3. 장바구니 추가 성공 메시지 표시
4. 상단 네비게이션의 장바구니 아이콘에 아이템 개수 반영

**기대 결과**: 상품이 장바구니에 추가되고 장바구니 개수가 증가

---

**단계 5: 장바구니 확인**
1. "Cart" 또는 장바구니 아이콘 클릭
2. 장바구니 페이지 표시
3. 추가한 상품들이 목록으로 표시됨
4. 상품별 가격, 수량, 소계 표시
5. 전체 총액 계산되어 표시됨

**기대 결과**: 장바구니에 추가한 상품들의 상세 정보가 정확하게 표시됨

| **신규 사용자 (Guest)** | 회원가입하지 않은 사용자 | 회원가입, 상품 검색, 장바구니 추가 |
| **기존 회원 (Registered User)** | 이미 회원가입한 사용자 | 로그인, 상품 검색, 장바구니, 주문 |
| **관리자 (Admin)** | MVP에서는 제외 | 추후 확장 범위 |

## 10. 공통 테스트 전략

### 10.1 테스트 설계 원칙
- **Page Object Model (POM)**: 모든 페이지에 대응하는 Page 클래스 작성
- **계층 분리**: Page Layer (화면 조작)와 Test Layer (검증)의 명확한 책임 분리
- **재사용성**: 공통 로직은 BasePage에 통합하여 중복 제거
- **안정성**: Explicit Wait, 안정적인 Locator 사용으로 테스트 안정성 확보

### 10.2 Page Layer 구조
- **BasePage**: 모든 Page 클래스가 상속하는 기본 클래스
  - WebDriver 관리
  - 공통 요소 조작 메서드 (클릭, 입력, 스크롤 등)
  - 공통 Wait 메서드 (요소 대기, 텍스트 대기 등)
  - 로깅 및 스크린샷 기능

- **기능별 Page 클래스**: 각 페이지마다 1개의 Page 클래스
  - UI 요소 Locator 정의 (상수)
  - 화면 조작 메서드 (입력, 클릭, 선택 등)
  - 값 조회 메서드 (텍스트, 속성 반환)
  - Assertion 절대 금지

### 10.3 Test Layer 구조
- **기능별 Test 클래스**: 각 기능마다 1개의 test 파일
  - Page 객체 활용하여 시나리오 구성
  - 데이터 준비 및 정리 (Setup/Teardown)
  - Assertion을 통한 결과 검증
  - 상세한 로깅

### 10.4 테스트 독립성 규칙
- **각 테스트는 단독 실행 가능**: 다른 테스트의 실행 여부와 무관하게 동작
- **테스트 간 상태 격리**: 한 테스트가 다른 테스트의 상태에 영향을 주지 않음
- **데이터 정리**: 테스트가 생성한 데이터는 테스트 내에서 정리
- **순서 의존성 제거**: 테스트 실행 순서가 변경되어도 결과 동일

**구현 방식**:
- pytest fixture (scope="function") 사용으로 각 테스트마다 새로운 브라우저 인스턴스 생성
- 각 테스트 시작 시 필요한 데이터 준비 (예: 로그인 후 검색 테스트 시작)
- 테스트 종료 시 생성한 데이터 삭제

### 10.5 Locator 선택 우선순위
CLAUDE.md에 정의된 우선순위를 엄격히 준수:

1. **id 속성** (가장 안정적)
2. **data-* 속성** (테스트용 속성)
3. **name 속성**
4. **안정적인 CSS Selector**
5. **상대 XPath** (마지막 수단)

**금지**: Full XPath 절대 금지 (유지보수 불가능)

### 10.6 Wait 처리 규칙
- **time.sleep() 절대 금지**: 비효율적이고 불안정함
- **Explicit Wait 기본 사용**: WebDriverWait + expected_conditions 활용
- **BasePage Wait 메서드 활용**:
  - `find_element_visible()`: 요소 가시성 대기
  - `click_when_clickable()`: 클릭 가능 상태 대기
  - `wait_for_element_presence()`: DOM 요소 나타남 대기
  - `wait_for_text()`: 텍스트 변경 대기

### 10.7 Assertion 위치
- **Page Layer**: Assertion 절대 금지 (값 반환만)
- **Test Layer**: Assertion 수행 (pytest assert 사용)
- **실패 메시지**: 기대값과 실제값을 명확히 포함

### 10.8 로깅 및 보고
- **로깅 도구**: Python logging 모듈 사용 (print() 절대 금지)
- **로그 레벨**:
  - DEBUG: 상세 진단 정보
  - INFO: 주요 액션 (로그인, 검색 등)
  - WARNING: 경고 (느린 응답 등)
  - ERROR: 오류 (요소 찾기 실패 등)
  - CRITICAL: 심각한 오류 (드라이버 크래시 등)

- **리포트**: pytest-html로 HTML 형식의 시각적 리포트 생성
- **스크린샷**: 테스트 실패 시 자동 스크린샷 저장

## 12. 테스트 데이터 관리 전략

### 12.1 테스트 계정
Automation Exercise에서 테스트 시 필요한 계정 정보:

**테스트 계정 종류**:
1. **신규 가입 계정**: 각 테스트마다 새로운 이메일로 가입
2. **기존 계정**: 재사용 가능한 테스트 계정 (선택사항)

**계정 정보 관리**:
- 방식: 환경변수 또는 JSON 파일 (`test_data/accounts.json`)
- 민감정보 (비밀번호) 보호: `.env` 파일로 관리 (git 미추적)
- 마스킹: 로그/리포트에서 비밀번호 표시 금지

**확인 필요**:
- Automation Exercise에서 동일 이메일로 여러 번 회원가입 가능한지 여부
- 이메일 인증이 필요한지 여부
- 테스트 계정 생성 제한 (가입 횟수 제한 등)

### 12.2 테스트 데이터 외부화
코드에 테스트 데이터를 하드코딩하지 않습니다:

**방식 1: JSON/YAML 파일**
```
test_data/
├── accounts.json          # 테스트 계정 정보
├── products.json          # 검색할 상품 정보
└── test_cases.json        # 테스트 데이터
```

**방식 2: pytest Fixture**
conftest.py에 테스트 데이터 fixture를 작성하여, 테스트 함수에서 fixture를 파라미터로 받아 사용하는 방식입니다. 이 방식을 사용하면 데이터가 테스트 코드와 분리되어 유지보수가 용이합니다.

**방식 3: 환경변수**
```
TEST_USER_EMAIL=test@example.com
TEST_PASSWORD=secure_password (git 미추적 .env에 저장)
```

### 12.3 데이터 정리 (Cleanup)
테스트가 생성한 데이터는 테스트 후 정리:

**정리 대상**:
- 테스트 용도로 생성한 계정
- 테스트 용도로 생성한 주문
- 임시 파일 (스크린샷, 로그 제외)

**정리 방식**:
- pytest fixture의 yield 후 (teardown) 단계에서 데이터 정리
- 또는 테스트 마크를 사용하여 별도 정리 스크립트를 통해 데이터 정리

### 12.4 민감정보 보호
- ❌ 코드에 비밀번호, 이메일 하드코딩 금지

- **Chrome만 사용**: 초기 단계는 Chrome + ChromeDriver (Firefox/Safari는 추후)
- **데스크톱 중심**: 모바일 테스트는 Phase 3 이후 (반응형 레이아웃은 인정)
- **인터넷 필수**: Automation Exercise는 공개 사이트이므로 인터넷 연결 필수

### 16.3 시간 및 리소스 제약사항
- **개발 리소스**: 1명 (AI 기반 자동화 개발)
- **예상 기간**: 3주 (Phase 1~3)
- **작업 시간**: 평일 정상 업무 시간 (추가 리소스 할당 시 단축 가능)

### 16.4 외부 의존성
- **Automation Exercise 사이트 가용성**: 테스트 실행 시 필수
- **인터넷 연결 속도**: 테스트 안정성에 영향
- **Chrome/ChromeDriver 버전 일치**: 필수 유지보수

## 17. 예상 위험 요소

### 17.1 기술적 위험
| 위험 요소 | 영향도 | 가능성 | 완화 방안 |
|---------|--------|--------|---------|
| **Locator 불안정** | 높음 | 중간 | 안정적인 Locator 우선순위 준수, id/data-* 속성 활용 |
| **동적 요소 처리** | 높음 | 높음 | Explicit Wait 적극 활용, BasePage Wait 메서드 강화 |
| **타이밍 이슈** | 높음 | 높음 | 적절한 타임아웃 설정 (10~20초), 요소 로드 완료 확인 |
| **네트워크 지연** | 중간 | 중간 | 재시도 로직 구현, 타임아웃 여유 설정 |
| **사이트 변경** | 중간 | 낮음 | 정기적인 Locator 검증, 페이지 구조 변경 모니터링 |
| **크로스 브라우저 호환성** | 중간 | 중간 | 브라우저별 테스트 케이스 분리, 호환성 가이드 제공 |

### 17.2 관리적 위험
| 위험 요소 | 영향도 | 가능성 | 완화 방안 |
|---------|--------|--------|---------|
| **요구사항 변경** | 높음 | 중간 | 명확한 PRD 작성, 변경사항 추적 |
| **일정 지연** | 중간 | 중간 | Phase별 마일스톤 설정, 정기적 진행 상황 점검 |
| **테스트 커버리지 부족** | 중간 | 낮음 | 기능별 최소 시나리오 개수 정의 |
| **문서 불일치** | 낮음 | 낮음 | PRD와 코드 연동성 검증 |

### 17.3 위험 완화 전략

**예방 활동**:
1. **정기적 Locator 검증**: 주 1회 사이트 방문하여 UI 변경 모니터링
2. **안정성 테스트**: 각 기능 완성 후 반복 실행하여 안정성 확인
3. **상세한 로깅**: 실패 시 원인 추적용 로그 남기기
4. **명확한 문서**: 기능별 PRD 상세 작성으로 구현 실수 최소화

**대응 활동**:
1. **Locator 변경 시**: 영향받는 모든 테스트 확인 후 수정
2. **사이트 오류 시**: 재시도 로직 또는 Wait 시간 증가
3. **테스트 실패**: 스크린샷 분석, 로그 검토 후 원인 파악 및 수정

## 19. 참고 및 확인 필요 사항

### 19.1 확인이 필요한 항목

#### 대상 사이트 관련
- **회원가입**: 
  - 이메일 인증이 필요한가? (필요하면 테스트 방식 재검토)
  - 동일 이메일으로 중복 가입이 가능한가?
  - 필수 입력 필드는 무엇인가? (이름, 주소 등)
  
- **로그인/로그아웃**:
  - 로그인 실패 시 표시되는 오류 메시지 내용?
  - 세션 타임아웃 시간은?
  - 로그아웃 후 리다이렉트 페이지는?

- **상품 검색**:
  - 검색 방식 (키워드, 필터링 등)?
  - 검색 결과 최대 표시 개수?
  - 검색 결과가 없을 때 메시지?

- **장바구니**:
  - 최대 담을 수 있는 상품 개수?
  - 중복 상품 추가 시 수량 증가 여부?
  - 장바구니 데이터 저장 방식 (세션/쿠키/DB)?

#### 테스트 환경 관련
- 테스트 계정 준비 방식 (자동 생성 vs 미리 준비된 계정 사용)
- 테스트 실행 시 사이트 부하 또는 제약사항 있는가?
- 테스트 데이터 정리 정책 (생성한 계정/주문 정리 필요여부)

#### 기술적 확인
- Automation Exercise 사이트의 동적 요소 정도 (JavaScript 활용도)
- 요소 로드 시간 (평균 로드 시간)
- 네트워크 지연에 대한 복원력 (재시도 메커니즘)

### 19.2 가정사항 (확인 전까지)
다음 항목들을 가정하여 PRD를 작성했습니다. 실제 사이트 확인 시 수정 필요:

1. 회원가입은 기본 정보 (이름, 이메일, 비밀번호)만 필요
2. 이메일 인증은 없음 (바로 계정 생성)
3. 로그인 실패 시 "Invalid email or password" 형식의 메시지 표시
4. 상품 검색은 키워드 기반
5. 장바구니는 쿠키/세션 기반으로 저장
6. 결제는 테스트 카드 정보로 가능

### 19.3 추후 갱신 계획
- 기능별 PRD 작성 시 실제 사이트 방문하여 세부사항 확인
- 확인된 내용은 프로젝트 전체 PRD에 반영
- Page Object 구현 시 Locator 상세 검증
